Scope Note
This repository is the Gateway/dashboard system, not the TireVix storefront application itself. It contains the merchant-facing API contract, PayPal integration, masking/rotation logic, webhook engine, admin controls, and the buyer-facing shield/popup bridge. Any storefront-specific inventory reservation or fulfillment behavior is external to this repo and is driven by the webhooks emitted from this Gateway.

1. System Architecture & Flow (Rotation & Masking)
High-Level Architecture
The payment path is:

Storefront calls Gateway POST /api/gateway/checkout
Gateway authenticates the store using X-Store-ID and X-API-Key
Gateway selects a merchant PayPal account using tenant rotation logic
Gateway masks/cloaks the product data before building the PayPal order
Gateway creates the PayPal order using the selected merchant account
Buyer is redirected through a shield domain or popup bridge
On buyer approval, the shield success page calls Gateway /api/gateway/execute
Gateway authorizes or captures the order at PayPal
Gateway persists transaction state in PostgreSQL
Gateway emits a signed webhook to the merchant storefront
PayPal asynchronous webhooks also arrive at Gateway and reconcile state
Primary implementation points:

app/api/gateway/checkout/route.ts
app/api/gateway/execute/route.ts
lib/merchant-rotation.ts
lib/paypal.ts
lib/masking.ts
proxy.ts
Rotation Logic
Rotation is tenant-scoped and controlled by tenants.rotation_strategy, rotation_interval, last_rotation_index, and last_rotation_at in prisma/schema.prisma.

Supported strategies in code:

VOLUME
TIME
SEQUENTIAL
Selection rules in lib/merchant-rotation.ts:

only ACTIVE and WARMING_UP accounts are eligible
warmup accounts have hard transaction caps
daily volume limits and optional overrides are enforced
soft-limit accounts are de-weighted
recent hourly concentration is smoothed
high-value orders favor established accounts
Operational caveat: rotationEnabled exists in admin controls, but the checkout hot path does not appear to enforce it. That setting should not be assumed to disable routing.

Item Masking / Cloaking
The real product name enters the Gateway through itemName on /api/gateway/checkout. The masking happens before PayPal payload creation.

Flow:

Real product name is accepted from merchant API request
Gateway selects merchant account
Gateway computes masked_item_name = maskItemName(itemName, fake_product_name?)
Gateway stores both:
transactions.original_item_name
transactions.masked_item_name
Only masked/sanitized values are sent to PayPal
Masking implementation:

lib/masking.ts
app/api/gateway/checkout/route.ts
lib/paypal.ts
Cloaking controls:

maskItemName(...): replaces real catalog language with generic descriptors or account-specific fake_product_name
maskBrandName(...): generates generic seller-facing branding
maskDescription(...): produces non-identifying descriptions
sanitizePayPalField(...): strips URLs, emails, phone numbers, markup, and risky text
randomizePayload(...) in lib/behavioral-randomization.ts:
slight unit-price jitter while preserving exact total
category rotation
line-item splitting
short time jitter before PayPal order creation
Shield / Cloak Layer
Shield domains are first-class infrastructure:

PayPal return_url and cancel_url are not merchant storefront URLs
they are generated by buildShieldUrls(...)
proxy.ts rewrites shield-domain traffic into safe internal app routes
buyer return flow is handled by:
app/order/result-client.tsx
app/checkout/popup/popup-client.tsx

Core Payment Endpoints
POST /api/gateway/checkout
File: app/api/gateway/checkout/route.ts

Request:

{
  "amount": 149.99,
  "currency": "USD",
  "itemName": "Michelin Pilot Sport 4S Tire",
  "intent": "AUTHORIZE",
  "customerEmail": "buyer@example.com",
  "buyerIp": "203.0.113.1",
  "buyerCountry": "US"
}
Response:

{
  "transactionId": "uuid",
  "approvalUrl": "https://www.paypal.com/checkoutnow?...",
  "flow": "REDIRECT",
  "popupUrl": null,
  "popupOrigin": null,
  "intent": "AUTHORIZE",
  "status": "PENDING",
  "merchantReturnConfigured": true
}
Behavior:

authenticates merchant
selects rotating merchant account
masks item data
creates PayPal order
persists transactions row as PENDING
POST /api/gateway/execute
File: app/api/gateway/execute/route.ts

Request:

{
  "transactionId": "uuid"
}
Response shape:

{
  "success": true,
  "status": "AUTHORIZED",
  "transactionId": "uuid",
  "authorizationId": "paypal-auth-id"
}
or:

{
  "success": true,
  "status": "COMPLETED",
  "transactionId": "uuid",
  "captureId": "paypal-capture-id"
}
Behavior:

idempotent execution after buyer approval
authorizes or captures based on stored intent
updates transaction state
persists outbound merchant webhook event
triggers webhook delivery
POST /api/gateway/capture
File: app/api/gateway/capture/route.ts

Request:

{
  "authorization_id": "paypal-auth-id"
}
Behavior:

manual capture for previously authorized transactions
requires Gateway transaction state AUTHORIZED
updates transaction to COMPLETED
emits payment.capture.completed
POST /api/gateway/refund
File: app/api/gateway/refund/route.ts

Request:

{
  "transaction_id": "uuid"
}
Behavior:

full refund only
requires Gateway transaction state COMPLETED
calls PayPal refund on stored capture id
updates transaction to REFUNDED
emits payment.capture.refunded
Important: partial refunds are not implemented in this repo.

POST /api/gateway/void
File: app/api/gateway/void/route.ts

Request:

{
  "authorization_id": "paypal-auth-id"
}
Behavior:

voids authorized but uncaptured payments
updates transaction to VOIDED
emits payment.authorization.voided
Critical inconsistency: code uses VOIDED, but the Prisma enum visible in prisma/schema.prisma does not include VOIDED. This is a schema/code mismatch that must be treated as high-risk.

GET /api/gateway/transactions/[transactionId]
File: app/api/gateway/transactions/[transactionId]/route.ts

POST /api/gateway/transactions/[transactionId]/replay
File: app/api/gateway/transactions/[transactionId]/replay/route.ts

Behavior:

replays latest or specific merchant webhook event

Inbound PayPal Webhook
POST /api/webhook/paypal
File: app/api/webhook/paypal/route.ts

Supported PayPal events:

PAYMENT.AUTHORIZATION.CREATED
PAYMENT.CAPTURE.COMPLETED
PAYMENT.CAPTURE.DENIED
PAYMENT.CAPTURE.REFUNDED
CUSTOMER.DISPUTE.CREATED
Verification process:

reads PayPal security headers
validates certificate URL host against allowed PayPal domains
resolves correct webhook_id
obtains OAuth token
calls PayPal verify-webhook-signature
rejects unverified requests
This verifies PayPal authenticity to the Gateway.

lib/webhook-delivery.ts

X-Webhook-Source

X-Webhook-Delivery-ID

Signature method:

HMAC-SHA256(secret, "${timestamp}.${rawBody}")
This repo signs outbound webhooks; merchant-side verification must replicate that exact algorithm.

3. Payment State Machine (Detailed Transitions)
Canonical Transaction States Observed
PENDING
AUTHORIZED
COMPLETED
FAILED
REFUNDED
DISPUTED
CANCELED
EXPIRED
VOIDED in route logic, but not clearly in schema
PENDING
Created at checkout after PayPal order creation.
DB effects:

stores original and masked item names
stores intent, merchant account, merchant return URLs, and paypal_order_id
stores checkout_expires_at
AUTHORIZED
Set by:

/api/gateway/execute when intent=AUTHORIZE
PayPal webhook PAYMENT.AUTHORIZATION.CREATED
DB effects:

status = AUTHORIZED
authorization_id set
authorized_at set
authorization_expires_at set
checkout_expires_at cleared
gateway_fee recorded
emits payment.authorization.created
Inventory note:
This repo does not reserve inventory itself. The merchant storefront is expected to reserve inventory when it receives payment.authorization.created.

COMPLETED
Set by:

/api/gateway/execute for instant capture flow
/api/gateway/capture for manual capture
PayPal webhook PAYMENT.CAPTURE.COMPLETED
DB effects:

status = COMPLETED
paypal_capture_id set
completed_at set
checkout_expires_at cleared
gateway_fee recorded
merchant_accounts.current_volume incremented
emits payment.capture.completed
Validation:

capture path expects PayPal status COMPLETED
transaction linkage relies on custom_id and PayPal related ids
Inventory note:
This repo does not finalize inventory. The merchant storefront is expected to finalize fulfillment/inventory on payment.capture.completed.

FAILED
Set by PayPal PAYMENT.CAPTURE.DENIED.

DB effects:

status = FAILED
failed_at set
checkout_expires_at cleared
merchant volume can be reversed if previously counted
emits payment.capture.denied
REFUNDED
Set by:

/api/gateway/refund
PayPal PAYMENT.CAPTURE.REFUNDED
DB effects:

status = REFUNDED
refunded_at set
merchant volume reversed
emits payment.capture.refunded
Important:

full refund supported
partial refund behavior is not present in this repo
no partial-inventory restoration logic exists here
VOIDED
Set by /api/gateway/void.

DB effects:

status = VOIDED
authorization/check-out expiry timestamps cleared
emits payment.authorization.voided
Inventory note:
Merchant storefront should release held inventory on this event.

CANCELED
Set by buyer cancel flow through markCheckoutCanceled(...).

DB effects:

PENDING -> CANCELED
canceled_at set
checkout_expires_at cleared
emits payment.checkout.canceled
EXPIRED
Set by cron recovery in lib/gateway-recovery.ts

Cases:

stale PENDING -> payment.session.expired
stale AUTHORIZED -> payment.authorization.expired
DISPUTED
Set by PayPal CUSTOMER.DISPUTE.CREATED.

DB effects:

status = DISPUTED
disputed_at set
emits payment.dispute.created
4. Next.js Client Integration Guide
Checkout Initialization
Merchant storefront should call Gateway POST /api/gateway/checkout server-to-server using X-Store-ID and X-API-Key. The response determines front-end behavior:

flow = REDIRECT: browser redirects to approvalUrl
flow = POPUP_BRIDGE: open popupUrl, which then redirects to PayPal
Relevant files:

app/api/gateway/checkout/route.ts
app/checkout/popup/popup-client.tsx
Success Flow
After approval, PayPal returns the buyer to a shield-domain success URL. The UI in app/order/result-client.tsx:

calls /api/gateway/execute
polls /api/gateway/browser-status/[transactionId]
treats AUTHORIZED and COMPLETED as success
redirects to merchant success URL if configured
posts popup bridge status to opener when applicable
Cancel Flow
On cancel:

client posts to /api/gateway/browser-result
Gateway marks transaction CANCELED
merchant cancel URL may be used for final redirect
Pending / Recovery UX
Pending is surfaced when:

execution has not finalized yet
webhook reconciliation is still catching up
browser polling has not observed terminal state yet
Recovery mechanisms:

immediate execute path
PayPal webhook reconciliation
retryable outbound merchant webhook delivery
cron-based expiration and replay processing
5. Critical Guardrails (Do Not Touch Rules)
Guardrail 1: Do Not Expose Real Catalog Identity to PayPal
Do not alter the masking pipeline in:

lib/masking.ts
lib/behavioral-randomization.ts
lib/paypal.ts
app/api/gateway/checkout/route.ts
Never send to PayPal:

real tire/product names
storefront brand/domain
merchant account identity beyond masked brand
customer PII in descriptive fields
Guardrail 2: Do Not Remove custom_id = transactionId
Webhook reconciliation depends on PayPal order linkage remaining stable. Changing this breaks execute/webhook correlation.

Guardrail 3: Do Not Replace Shield Return URLs with Storefront URLs
buildShieldUrls(...), proxy.ts, popup bridge pages, and browser result/status routes form the cloaking layer. Direct merchant return URLs to PayPal would bypass masking and can expose the storefront/payment pattern.

Guardrail 4: Do Not Change Webhook Event Names or Payload Keys Casually
The storefront integration depends on stable event contracts. Preserve:

event_id
event_type
transaction_id
paypal_order_id
authorization_id
paypal_capture_id
timestamp semantics
signature headers
Guardrail 5: Do Not Change Merchant Auth Headers
X-Store-ID and X-API-Key are the integration contract for all merchant server-to-server calls.

Guardrail 6: Do Not Remove Durable Webhook Persistence
webhook_events and webhook_deliveries are required for replay, retries, auditing, and merchant reconciliation.

Guardrail 7: Do Not Assume Inventory Logic Lives Here
This repo owns payment truth, not inventory truth. Inventory reservation/finalization/restoration must be driven by storefront webhook handlers, not inferred from browser redirects.

Guardrail 8: Treat the VOIDED Schema Mismatch as a Live Risk
Route logic expects VOIDED; schema snapshot does not clearly define it. Any migration or enum cleanup must be handled carefully before touching void flows.

Guardrail 9: Do Not Assume Admin Flags Are Fully Enforced
rotationEnabled exists, but enforcement is not obvious in the checkout hot path. Do not document or rely on it as a hard kill switch without fixing that explicitly.

Guardrail 10: Do Not Rewrite PayPal Verification Logic Lightly
Inbound PayPal webhook verification, allowed cert host validation, per-account webhook id resolution, and merchant/store signing are security-critical.

Final Architectural Conclusions
This codebase is not a generic checkout app. It is a controlled payment-orchestration layer with four coupled invariants:

merchant account rotation must stay deterministic and limit-aware
masking/cloaking must prevent real storefront/catalog exposure to PayPal
shield-domain browser flow must remain the only buyer-facing return path
payment truth must be propagated to storefronts only through signed, durable webhooks
Any future developer or AI working in this repo should treat checkout -> masking -> PayPal payload -> execute -> webhook persistence -> merchant webhook delivery as a single protected chain. Breaking any link in that chain risks payment failures, webhook drift, merchant desync, or unwanted PayPal exposure.
